MZS / PSB Format

The compression/encryption wrapper and binary resource format used by m2engage.

File Extension Convention

ExtensionContents
.psb.mMZS-encrypted PSB config/motion file
.nut.mMZS-encrypted Squirrel script
.psbRaw (decrypted) PSB binary
.nutRaw Squirrel source code

MZS Encryption Layer

The .m suffix indicates MZS encryption. This is a simple two-step process:

MZS File Structure +-----------+------------------------------------------+ | Header | magic: "mzs\0" (4 bytes) | | | uncompressed_size (4 bytes, little-endian) | +-----------+------------------------------------------+ | Payload | XOR-encrypted zstd-compressed data | +-----------+------------------------------------------+ Decryption Pipeline: .psb.m file ──XOR decrypt──> zstd blob ──decompress──> .psb binary Encryption Pipeline: .psb binary ──zstd compress──> zstd blob ──XOR encrypt──> .psb.m file

XOR Cipher

The payload uses a repeating XOR buffer derived from the game key and the complete filename: 

Game key: "8!7ZZnJAr/wfc"
Filename: lowercase basename, including extensions (e.g. "title_prof.psb.m")
Seed: MD5(UTF-8(game_key + filename))
MT19937 seed words: four little-endian uint32 values from that digest
XOR buffer: first 64 bytes of MT19937 output (little-endian uint32 words)

For each payload byte at position i:
  encrypted[i] = compressed[i] ^ xor_buffer[i % 64]
Filename matters! The key derivation includes the complete lowercase basename, including .psb.m or .nut.m, but not its directory. This means a file encrypted as title_mode_top.psb.m cannot be decrypted if renamed to other_name.psb.m. Keep the intended filename when extracting/building, or repack the content under its new filename.

Zstandard Compression

After XOR decryption, the payload is a standard zstd-compressed blob. The tool defaults to compression level 3; this is a tool setting, not a format requirement. The header records the decompressed byte count, not the compressed payload length. The magic bytes after decryption should be 0x28 0xB5 0x2F 0xFD (zstd frame magic).

PSB Binary Format

PSB (PackageSuB) is M2's proprietary binary format for structured data. Think of it as a binary JSON with support for embedded binary resources (textures, etc.).

PSB Header

Offset Size Description ────── ──── ─────────── 0x00 4 Magic: "PSB\0" 0x04 2 Version (uint16; commonly 3 or 4) 0x06 2 Flags (uint16) 0x08 4 Key offsets table offset (v1; legacy header field in v2+) 0x0C 4 Key-name trie/blob offset 0x10 4 String offsets table offset 0x14 4 String data offset 0x18 4 Resource/chunk offsets table offset 0x1C 4 Resource/chunk sizes table offset 0x20 4 Resource/chunk data base offset 0x24 4 Root object tree offset 0x28 4 Header Adler-32 checksum (v3+) 0x2C 4 B-stream offsets table offset (v4+) 0x30 4 B-stream sizes table offset (v4+) 0x34 4 B-stream data base offset (v4+)

Resources / Textures

PSB files can embed binary resources (typically RGBA textures). These are stored in a separate chunk area after the main tree data. Motion PSBs use this to embed sprite sheet textures.

Resources are referenced in JSON as special "stream:NAME" keys that map to external PNG files during extract, and get re-embedded during build.

JSON Representation

When extracted with mzstool.py, PSB files become JSON with a resource directory alongside for any embedded textures:

Extracted layout title_mode_top.psb.m | |── extract v title_mode_top/ |- title_mode_top.json # Config data as JSON \- (no resources for config-only PSBs) title_jp_titleselect_jp.psb.m | |── extract v title_jp_titleselect_jp/ |- title_jp_titleselect_jp.json # Motion data as JSON |- tex#000.png # Sprite sheet 1 (1024x1024) \- tex#001.png # Sprite sheet 2 (1024x1024)

Round-Trip Fidelity

An extract → build round trip can preserve the decoded resource while producing different binary bytes. Differences can include:

  • Different zstd compression output (different compressor version/settings)
  • Potentially different PSB internal layout (string table ordering, padding)
  • XOR encryption is deterministic given the same input

Verified configuration and motion round trips can be usable in m2engage, but successful JSON conversion alone does not prove compatibility. Check the rebuilt decoded values, embedded resource data, filename-derived key, and the resource types exercised by the engine.
