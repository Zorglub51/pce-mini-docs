Save System

How m2engage persists system settings, game save states, SRAM, and replay data. Covers the backup manager, file naming conventions, and the autosave lifecycle.

1. Architecture Overview

m2engage combines Squirrel save-management code with native storage and emulator bindings. g_systemdata is an instance of the Squirrel SystemData class (systemdata.nut), and BackupStatedata is defined in backup_statedata.nut. They coordinate native Struct, BackupManager, backup segments, and emulator operations.

Save System Architecture g_systemdata (Squirrel SystemData object) | |-- System Backup Manager | |-- SYSTEM_DATA (1 slot) ← system-wide settings | |-- SYSTEM_ARCHIVE (1 slot) ← system archive | \-- SOUND_PLAY_LIST (2 slots) ← BGM/sound config | \-- Title Backup Manager |-- TITLE_DATA (1 slot) ← per-title settings |-- TITLE_SOUND_PLAY_LIST (1 slot) ← per-title sound |-- EMU_STATE_L (500 slots) ← large save states |-- EMU_STATE (500 slots) ← normal save states \-- EMU_REPLAY (99 slots) ← input replay data Physical storage: save/data_{type}_{slot}.bin + save/meta_{type}_{slot}.bin

2. Backup Segments

Each type of save data is a segment with a numeric type ID, a slot count, and a format version. Defined in const.nut:

Segment Type ID Slots Version Description
SYSTEM_DATA 0 1 0x00010012 System-wide settings (language, screen, pad, etc.)
SYSTEM_ARCHIVE 1 1 0x00010010 System archive data
SOUND_PLAY_LIST 2 2 0x00010010 Sound/BGM playlist settings
IDs 3–7 reserved (dummy)
TITLE_DATA 8 1 0x00010018 Per-title settings (game config, medals, SRAM)
TITLE_SOUND_PLAY_LIST 9 1 0x00010010 Per-title sound settings
ID 10 reserved (dummy)
EMU_STATE_L 11 500 0x00010010 Large emulator save states
EMU_STATE 12 500 0x00010010 Normal emulator save states
EMU_REPLAY 13 99 0x00010010 Input replay recordings
Multi-title packs For packages with multiple titles (e.g., PCE Mini with 58 games), the title-specific segments (EMU_STATE, EMU_REPLAY) are multiplied per title. The constant NUM_EMU_DATA_SEGMENT_TYPES = 2 controls how many segment types are duplicated per additional title.

3. File Naming Convention

Backup Manager Files (Normal Save System)

The native backup manager writes to a save/ directory relative to the m2engage working directory. On the original hardware, this is /usr/game/save/.

Each save slot produces two files:

save/data_{TYPE:03d}_{SLOT:04d}.bin    ← actual save data
save/meta_{TYPE:03d}_{SLOT:04d}.bin    ← metadata (404 bytes, PSB format)

TYPE is the BackupSegmentTypes enum value (zero-padded to 3 digits). SLOT is the slot index within that segment (zero-padded to 4 digits).

Example files

FileSegmentSizeDescription
data_000_0000.bin SYSTEM_DATA ~1.2 MB System settings (language, screen, wallpaper, etc.)
data_008_0000.bin TITLE_DATA ~1.2 MB Title settings (per-game config, medals, SRAM)
data_012_0000.bin EMU_STATE slot 0 ~876 KB First emulator save state
data_012_0001.bin EMU_STATE slot 1 ~876 KB Second emulator save state
data_013_0000.bin EMU_REPLAY slot 0 varies First replay recording
meta_008_0000.bin TITLE_DATA meta 404 bytes PSB-format metadata for the title data

Meta Files

Each meta_*.bin is a small PSBv3 structure containing save metadata. The examined metadata files are 404 bytes; their structure and digest location should be parsed rather than inferred from that observed size:

FieldTypeDescription
TimeStamp integer Unix timestamp of when the save was created
FileSize integer Size of the corresponding data_*.bin file in bytes
OriginalSize integer Original payload size. In the examined raw backup files it equals FileSize; this does not imply that every buffer nested inside the payload is uncompressed.
FileVersion integer Format version (0x10200 = 66048)
Digest 16 bytes MD5 digest of the complete corresponding data file
CryptMagic integer Encryption flag (0 = no encryption)

SRAM vs Emulator State

Game saves involve two distinct types of data that serve different purposes:

SRAM (in TITLE_DATA, type 008)Emulator State (types 011/012)
What it is The game’s own battery-backed save RAM. On real hardware, this is a small chip on the HuCard that persists between power cycles. A complete hardware snapshot — CPU registers, all system RAM, VRAM, audio registers, I/O state, timers. Like pausing the entire machine at a specific frame.
What it stores Whatever the game itself writes: high scores, save game progress, character stats, unlocks. The exact state of the emulated console at one instant. Screen contents, audio position, controller state — everything.
Real-world analogy A memory card A VM snapshot / freeze-frame
Size An 8,192-byte shared image buffer per 8,448-byte SRAM block; compression depends on the adapter setting Reserved emulator payload: 256 KiB (HuCard/SGX) or 1.5 MiB (CD), plus headers and thumbnail storage
Per save slot? Four tagged SRAM entries share one image buffer. Their count does not establish a one-to-one mapping to the four pause-menu save-state slots. Yes — each slot is a separate data_0XX_YYYY.bin file
Where stored Inside data_008_0000.bin (the 1.29 MB TITLE_DATA file, struct_sram_data arrays) Individual files: data_012_YYYY.bin (HuCard) or data_011_YYYY.bin (CD)
Separate hardware state and SRAM management An emulator state captures the emulated machine. The separate SystemDataSramData/EmuSram path synchronizes SRAM only when sram_support is enabled. The examined stock profile defaults this flag to false, so the allocated SRAM bank alone does not prove that the game uses that synchronization path. During state loading, profile flags can preserve the current SRAM or skip its comparison. See SRAM profile parameters.

Data File Layout — Game Saves (Types 011/012)

Game save state data files have a fixed layout with four regions:

Game Save Data File Layout Header 0x000 – 0x2FF 768 bytes |-- 0x050: Game ID string (e.g. "GAME000", "GAME031") |-- 0x040: Checksum \-- Other emulator metadata (version, flags, tick counts) Emulator State 0x300 – thumb_offset Full CPU/RAM/VRAM/audio snapshot of the emulated hardware. Everything needed to resume gameplay exactly where you left off. Screenshot thumb_offset + 8 bytes |-- 4 bytes: width (320) |-- 4 bytes: height (240) \-- 230,400 bytes: raw RGB pixel data (320 × 240 × 3) Padding After screenshot to end of file All zeros. Reserved space, currently unused.
Save Type Total Size Emu State Thumb Offset Screenshot Padding
012 (HuCard) 895,848 bytes 256 KB 0x040300 225 KB 393 KB
011 (CD) 2,206,568 bytes 1.5 MB 0x180300 225 KB 393 KB
Why is the CD state buffer larger? The templates reserve 0x180000 bytes for CD emulator data and 0x40000 for HuCard/SGX data. These are reserved capacities, not measured compressed state sizes or a sixfold ratio between complete save files. CD configurations also include disc-system RAM, ADPCM state, and, with an Arcade Card, additional RAM.

Data File Layout — Title Data (Type 008)

The TITLE_DATA file (data_008_0000.bin) is raw uncompressed binary — not zlib-compressed, not PSB-formatted. It starts directly with the struct version (0x00010018) and follows the schema defined in struct_systemdata_title.json.

In the examined stock layout, the file is 1,291,396 bytes. The first 0x5e84 bytes contain settings, flags, work areas, and per-game configuration. The SRAM array then contains 150 complete blocks of 8,448 bytes each. These offsets apply to that schema; changing the struct template changes the binary layout.

RegionFile offsetSize
Settings and work areas0x000024,196 bytes
SRAM blocks (150)0x5e841,267,200 bytes

One SRAM block contains four 64-byte struct_sram_entry headers and an 8,192-byte shared image buffer. Each header stores an 8-byte tag, an image offset, encoded and decoded sizes, and 44 padding bytes. Entry offsets refer into that shared image buffer. The full block size is 4 × 64 + 8192 = 8448 bytes; the buffer is not four separate 8 KB images. The schema preallocates all 150 blocks, including unplayed games.

SRAM compression is not encryption m2epi.sram_crypted selects zlib compression/decompression of SRAM buffers, despite its name. It is separate from MZS encryption and from metadata CryptMagic. sram_common and systemdata_sram_data_no select the working SRAM bank; sram_support enables the Squirrel synchronization path and does not add or remove hardware RAM in the emulated machine.

Per-Game Save Slot Numbering

Each game has 4 save state slots (numbered 0–3). The slot number in the filename encodes both the game’s position in the lineup and which of the 4 slots is used. The file type (011 vs 012) depends on the game’s platform:

Type ID Segment Platform Determined by
011 EMU_STATE_L CD games (CD-ROM², Super CD, Arcade CD) csize ≥ 2 in title_mode_top
012 EMU_STATE HuCard / SG Card games csize < 2 in title_mode_top

Slot Calculation

The slot number in the filename is calculated as:

// JP / PCE lineup (getLinenpIndexOffset() = 0):
slot = game_index × 4 + save_slot       // range: 0–199

// US / TG16 lineup (getLinenpIndexOffset() = LINEUPMAX = 50):
slot = (50 + game_index) × 4 + save_slot  // range: 200–399

// Where:
//   game_index  = sorted position in lineup (0–49)
//   save_slot   = which of the 4 save slots (0–3)
//   LINEUPMAX   = 50 (max games per lineup)

The corresponding Squirrel code in mode_title_select.nut: 

local sortindexLineup = s_indextable[selectindex] + getLinenpIndexOffset();
local fileid = i + (sortindexLineup * 4);
// i = save slot (0-3)
// getLinenpIndexOffset() returns 0 for JP, 50 for US

Worked Examples

Filename Type Slot Lineup Game Index Save Slot Meaning
data_012_0000.bin HuCard 0 JP 0 0 First JP HuCard game, slot 0
data_012_0016.bin HuCard 16 JP 4 0 5th JP HuCard game, slot 0
data_011_0019.bin CD 19 JP 4 3 5th JP CD game, slot 3
data_012_0200.bin HuCard 200 US 0 0 First US HuCard game, slot 0
data_011_0212.bin CD 212 US 3 0 4th US CD game, slot 0
500 slots per segment Each segment type (EMU_STATE and EMU_STATE_L) has 500 slots total. JP games use slots 0–199 and US games use slots 200–399, leaving slots 400–499 unused. This allows up to 50 games per lineup with 4 save slots each.

Host Save Files (Debug/Test Menu)

The host_save_* functions (accessible via test menu) use a different naming scheme, writing directly to the working directory: 

// With timestamp:
state_{rom_name}_{YYYYMMDD}_{HHMMSS}.bin
// Example: state_R-TYPE.pce_20260208_143022.bin

// Without timestamp:
state_{rom_name}.bin
// Example: state_R-TYPE.pce.bin

// Replay files:
replay_{rom_name}.bin
// Example: replay_R-TYPE.pce.bin

// Screenshots:
screenshot_{rom_name}_{YYYYMMDD}_{HHMMSS}.bmp

The ROM name comes from _get_rom_name_for_host(), which returns s_rom_fileparse.name + s_rom_fileparse.ext (e.g., "R-TYPE.pce") or "image" as fallback.

5. Emulator State Data (Save States)

Each emulator save state is a binary Struct with this layout:

State Data Struct (struct_statedata.psb) _00_header |-- _00_version BackupStructVersion (0x00010010) |-- _01_data_version EmuVersion (emulator compatibility) \-- _02_data_size Size of state data _01_added_value |-- _00_title_id Game title identifier |-- _01_tick_HI Timestamp (high 32 bits of system tick) |-- _02_tick_LW Timestamp (low 32 bits of system tick) |-- _05_sram_flag SRAM enabled/disabled |-- _06_region Region tag ("JAPAN", "USA", etc.) |-- _07_bitflag Flags (0x0001 = original_bug_emulation) |-- _08_boot_timer Boot timer value \-- _11_screen_mode Active screen mode _01_setting_game Game configuration snapshot _04_medalsystem_1gamework Per-game achievement data _05_thumbnail |-- _00_width Thumbnail width (pixels) |-- _01_height Thumbnail height (pixels) \-- _02_pixels Thumbnail image data (230,400 bytes: 320 × 240 RGB)

Save State Operations

The Squirrel BackupStatedata class coordinates native emulator capture/restore and backup-segment operations:

OperationMethod Chain
Save get_struct() → clear() → from_emu() (capture state + thumbnail + header) → segment.singlesave()
Load segment.singleload() → check_header() (validate version) → compare_emu() (detect differences) → to_emu() (apply to emulator)
Delete delete_state_data(slot_index)
Header validation When loading a save state, check_header() verifies the BackupStructVersion and EmuVersion for compatibility. If the version doesn't match, the load is rejected. The compare_emu() step detects differences (SRAM, region, bug flags) and may show a confirmation dialog.

7. Autosave System

Autosave is coordinated by the Squirrel g_systemdata object and its TryAutosave() method in systemdata_saveload.nut. It saves system and title data — not emulator save states (those require explicit user action).

Trigger Points

LocationCallWhen
mode_normal.nut:33 TryAutosave() After exiting gameplay (SRAM/flags may have changed)
mode_title_select.nut:331 TryAutosave(true) After first-run language selection
mode_title_select.nut:348 TryAutosave(true) After language selection (non-first-run)
mode_main.nut:129 TryAutosave(true) After 3D display mode change
mode_title_select_setting.nut:1063 TryAutosave(true) After data initialization dialog
mode_title_select_setting.nut:1162 TryAutosave(true) After screen effect settings change
mode_title_select_settinglang.nut:208 TryAutosave(true) After language change in settings

TryAutosave(force)

// Queued autosave (after gameplay)
::g_systemdata.CheckValueChangeAutosave();  // mark changed segments
::g_systemdata.TryAutosave();               // save marked segments

// Forced autosave (after settings change)
::g_systemdata.TryAutosave(true);           // save immediately
Title identity and initialized backup structures must agree Changing the active dev_id also changes title/profile lookup and resource paths. An incomplete title definition or inconsistent initialized backup structures can therefore break saving. The stock scripts do not establish a general rule that every custom ID fails, or that temporarily changing it to 40 is a safe universal fix.

9. Struct Template PSBs

Save data structures are defined by PSB template files that specify the binary layout (field names, types, sizes). The native code loads these at init time:

Template PSBUsed For
system/config/struct_systemdata.psb SYSTEM_DATA segment structure
system/config/struct_systemdata_title.psb TITLE_DATA segment structure (single title)

system/config/struct_statedata.psb EMU_STATE segment structure
system/config/struct_statedata_l.psb EMU_STATE_L segment structure (large states)
system/config/struct_replaydata.psb EMU_REPLAY segment structure
system/config/struct_sound_play_list.psb SOUND_PLAY_LIST segment structure
system/config/struct_savedata_dummy.psb Dummy/placeholder structure for reserved segments

system/config/struct_statedata_extend.psb Extended state data fields
system/config/struct_setting_game_image.psb Per-game settings structure
Binary, not JSON These template PSBs define the schema of each save data type. The native Struct class uses them to create typed binary buffers. The actual save data is written as raw binary, not as PSB/JSON.
