MZS / PSB Format

The encryption wrapper and binary config format used by all m2engage data files.

File Extension Convention

ExtensionContents
.psb.mMZS-encrypted PSB config/motion file
.nut.mMZS-encrypted Squirrel script
.psbRaw (decrypted) PSB binary
.nutRaw Squirrel source code

MZS Encryption Layer

The .m suffix indicates MZS encryption. This is a simple two-step process:

MZS File Structure +-----------+------------------------------------------+ | Header | magic: "mzs\0" (4 bytes) | | | compressed_size (4 bytes, little-endian) | +-----------+------------------------------------------+ | Payload | XOR-encrypted zstd-compressed data | +-----------+------------------------------------------+ Decryption Pipeline: .psb.m file ──XOR decrypt──> zstd blob ──decompress──> .psb binary Encryption Pipeline: .psb binary ──zstd compress──> zstd blob ──XOR encrypt──> .psb.m file

XOR Cipher

The encryption is a simple repeating XOR with a key derived from the filename: 

Key base: "8!7ZZnJAr/wfc"
Key length: 131 bytes (derived by repeating + hashing)

For each byte at position i:
  encrypted[i] = plain[i] ^ key[i % key_length]
Filename matters! The key derivation includes the filename (without extension). This means a file encrypted as title_mode_top.psb.m cannot be decrypted if renamed to other_name.psb.m. Always keep the original filename when extracting/building.

Zstandard Compression

After XOR decryption, the payload is a standard zstd-compressed blob. Default compression level for building: 3. The magic bytes after decryption should be 0x28 0xB5 0x2F 0xFD (zstd frame magic).

PSB Binary Format

PSB (PackageSuB) is M2's proprietary binary format for structured data. Think of it as a binary JSON with support for embedded binary resources (textures, etc.).

PSB Header

Offset Size Description ────── ──── ─────────── 0x00 4 Magic: "PSB\0" 0x04 4 Version (typically 3 or 4) 0x08 4 Flags / encryption marker 0x0C 4 String offsets table offset 0x10 4 String data offset 0x14 4 Resource offsets table offset 0x18 4 Resource data offset (chunk offsets) 0x1C 4 Resource data offset (chunk lengths) 0x20 4 Root object tree offset 0x24 4 Total resource data size

Resources / Textures

PSB files can embed binary resources (typically RGBA textures). These are stored in a separate chunk area after the main tree data. Motion PSBs use this to embed sprite sheet textures.

Resources are referenced in JSON as special "stream:NAME" keys that map to external PNG files during extract, and get re-embedded during build.

JSON Representation

When extracted with mzstool.py, PSB files become JSON with a resource directory alongside for any embedded textures:

Extracted layout title_mode_top.psb.m | |── extract v title_mode_top/ |- title_mode_top.json # Config data as JSON \- (no resources for config-only PSBs) title_jp_titleselect_jp.psb.m | |── extract v title_jp_titleselect_jp/ |- title_jp_titleselect_jp.json # Motion data as JSON |- tex#000.png # Sprite sheet 1 (1024x1024) \- tex#001.png # Sprite sheet 2 (1024x1024)

Round-Trip Fidelity

The extract → build pipeline produces valid but not binary-identical files. Differences include:

  • Different zstd compression output (different compressor version/settings)
  • Potentially different PSB internal layout (string table ordering, padding)
  • XOR encryption is deterministic given the same input

Despite binary differences, round-tripped files are functionally equivalent and work correctly with m2engage.
