title_mode_top config

The original PC Engine Mini menu catalogue: game identities, translated names, packaging, sorting and the screen crop applied before a game starts.

Jump to: all game fields · packaging · video crop tables · language and launch · R-Type example.

Scope and File Location

040/config/title_mode_top.psb.m

The retail resource examined here contains 200 items. Its JSON root is the table shown below, with no extra root wrapper. This is the menu list; the emulated machine and ROM are selected separately by title_prof.

Behaviour was traced through the decrypted stock mode_title_select.nut and mode_demo.nut, and the ARM video descriptor getters. Native addresses below refer to the m2engage build with SHA-256 b02848f66b82f8ac3090db523c4db9633508f9e3f53c7dc0ee3d01ce8aee8792. They establish the behaviour of this build, rather than a universal schema for every M2 title.

Top-Level Structure

{
  "items": [ ... ],              // retail layout: four sections of 50
  "motion_basename": "title_grandmenu",
  "motion_chara": "grandmenu",
  "motion_label": "stand",
  "scroll_frame": 10,
  "scroll_variable": "gametitle_normal",
  "titleNum": 34,                // active PCE-lineup entries
  "titleNumTG": 24               // active TG16-lineup entries
}

titleNum and titleNumTG determine the active entries in each lineup. The shipped selection script uses a fixed LINEUPMAX = 50 to locate the sections; increasing a count beyond 50 does not extend that layout. Keep unused slots as DUMMY entries, including those visited by the attract-mode loop.

Retained keys are not automatically required settings. The five motion_*/scroll_* keys above exist in the retail resource, but no active reader for them was found in the shipped PC Engine selection/demo path. Menu motion resources are selected elsewhere in those scripts. There is no evidence that these five keys form a mandatory native parser schema.

The Four Sections

The first 100 items contain the two lineups' base entries. The next 100 provide the non-Japanese name and sort views. These views are not four independent sets of games.

Sorting Invariants

For each lineup and language view, each active sorting field should be a permutation of 0…N−1, where N is that lineup's active count. The script builds an inverse lookup with s_indextable[rank] = item_index. Duplicate ranks overwrite another entry and leave holes. Ranks outside the active range can make an entry inaccessible; sufficiently large or negative ranks can cause an array error. The original array has 60 elements, so an out-of-active-range value is not automatically an immediate bounds exception.

DUMMY entries outside the active count are not included in this sorting loop. The stock data gives them their within-section position (0–49). Keeping that convention does not make arbitrary active sort ranks safe.

ScreenMode: Exact Crops by Core

The menu calls SetScreenMode and SetEmuScreenOffsetX/Y before launch. Each native core then builds a video descriptor from its current raster dimensions. ScreenMode changes the part of that raster sent for display. It does not change the ROM's VDC registers, game logic speed or HDMI output resolution.

Each cell below is visible width @ source X, in pixels, with zero additional EmuOfsX/Y. “Full” keeps the original raster width. Heights are unchanged by ScreenMode. Other raster widths keep their full width in these branches.

The same mode number does not mean the same crop in every core. For example, mode 1 keeps a 272-pixel TG16 raster in full, but TG16CD displays 256 pixels from X=16. Mode 4's 512-pixel TG16 crop starts at X=160, not the centred X=128.

When EmuOfsX and EmuOfsY Take Effect

The getters add these signed values to the descriptor's source position. The shared renderer (0x348e8–0x3499a) applies them only if the descriptor's explicit-crop flag is set. If no crop is active, it centres the full raster and discards those offset values. A separate GT-screen property can create a vertical crop and therefore also activate explicit offsets.

For example, TG16 mode 4 on a 352-pixel raster samples 336 pixels starting at X = 8 + EmuOfsX. Setting EmuOfsX = 2 samples from X=10. In mode 0 on the same raster, there is no horizontal crop, so the added offset is ignored unless another crop has set the flag. These parameters move the source window, not the menu UI.

Language Views and Launch Settings

getLanguageIndexOffset() selects the translated names and sorting fields: 0 or 100 for the language, plus 50 for the TG16 lineup. Most artwork/card settings and the normal launch path use getLinenpOffsetConfigData() instead. That function adds only the lineup offset (0 or 50) to the sorted item index.

Consequently, changing the language-view copy of ScreenMode at item i + 100 does not change a normal launch of item i. The retail demo loop visits base items 0–99 directly and applies each selected item's demo_time, ScreenMode and offsets. Preserve matching identities across the two language views, but do not assume every duplicated field is a separate override.

Practical Example: R-Type

Retail item 61 is GAME031 (R-Type) with ScreenMode = 4 and zero offsets. Its translated-view copy, item 161, contains mode 0. A normal launch still reads item 61, including with an English or French UI, and therefore uses mode 4.

The stock TG16 core produces a 352 × 240 raster for R-Type's selected video clock. Mode 4 shows 336 × 240 from X=8, removing eight columns at each side. The ROM itself can program active widths of 336 or 320 pixels. When the active width is 320, eight border columns on each side remain inside the 336-pixel display window.

The game's title_prof entry contains only arch = "tg16", country = "us", preamp = 1.0 and its ROM path. It has no special tg16_option, tg16_hblank or overdrive override. The observed framing comes from this menu crop and the ROM's hardware setup; no R-Type-specific filename branch was found in the engine.

DUMMY Entries

Unused retail slots have the same 24 keys. Their regionTag, name and tname are "DUMMY", alternate tags are "NO", and each sort rank matches the slot's position within its 50-item section. A representative template is:

{
  "EmuOfsX": 0, "EmuOfsY": 0, "ScreenMode": 0,
  "action": "Boot", "ccolor": 0, "copy": "", "csize": 0,
  "demo_time": 6180, "desc": "", "dev_name": "PceMini",
  "image": 34, "name": "DUMMY", "players": 1,
  "regionTag": "DUMMY", "regionTagE": "NO",
  "regionTagS1": "NO", "regionTagS2": "NO",
  "sor_date": 34, "sor_demo": 34, "sor_genr": 34,
  "sor_name": 34, "sor_pnum": 34,
  "titlebar": 0, "tname": "DUMMY"
}

This example represents within-section slot 34. DUMMY player counts are observed data, not proof that every field is required or that a different value inherently crashes the engine.
