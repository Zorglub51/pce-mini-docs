Squirrel VM & Filesystem

Complete reference for filesystem access, resource loading, and I/O functions available to Squirrel scripts running inside m2engage.

No Direct File I/O The Squirrel VM in m2engage has no direct filesystem access. Standard Squirrel I/O functions (dofile, loadfile, compilestring, io.open) are stripped from the VM. All file operations go through native C++ bindings exposed as global functions or class methods.

1. Path Resolution

m2engage uses a virtual path system that maps short relative paths to actual filesystem locations. The mapping depends on the active dev_id (title pack) and configuration rules in game_content.psb.

conv_path(short_path, dev_id)

Converts a relative path to a full path by prepending system/ or {dev_id}/ based on path classification rules. 

// Signature
function conv_path(short_path, dev_id = 0)
// Returns: string (full path)

// Examples
conv_path("config/title_mode_top.psb")     // → "040/config/title_mode_top.psb"
conv_path("script/utils.nut")              // → "system/script/utils.nut"
conv_path("state/save.dat")               // → "040/state/save.dat"
conv_path("motion/bg01.psb", 42)          // → "042/motion/bg01.psb"

Resolution Rules

Three config lists in game_content.psb control where paths resolve:

Config Key Behavior Values (PCE Mini)
forceAbsolutePath Paths starting with these prefixes are always system/ ["system/"]
titleOnlyDir Paths starting with these prefixes are always {dev_id}/ ["manual/", "state/"]
titleOnlyFile Specific filenames that are always title-only [] (empty)

For paths not matching any rule, conv_path() first checks {dev_id}/, then falls back to system/.

Gotcha: "script/" resolves to system/ The script/ prefix is NOT in titleOnlyDir, so conv_path("script/pack_config.nut") resolves to system/script/pack_config.nut, not 042/script/pack_config.nut. To load title-specific scripts, build the path explicitly: 
local path = format("%03d/script/pack_config.nut", ::get_current_title_dev_id());

conv_checked_path(short_path, dev_id, bDeleteExtM)

Like conv_path() but verifies the file actually exists. Returns null if the file is not found. 

// Signature
function conv_checked_path(short_path, dev_id = 0, bDeleteExtM = false)
// Returns: string (full path) or null

// Check order:
// 1. FileUtil.getExistFileDirInMountArchive(path)  — mounted archives
// 2. GameContent.getExistFileDir(path)              — extracted directories
// Returns: directory_prefix + short_path, or null
When to use which Use conv_path() when you know the file exists (e.g., loading a required config). Use conv_checked_path() when the file may not exist and you need to check (e.g., optional pack_config.nut overrides, platform-specific resources).

2. Resource & Config Loading

Resource Class (Native)

The primary mechanism for loading PSB files. Resources are loaded asynchronously. 

// Create and load
local rsc = Resource();
rsc.load("040/config/title_mode_top.psb.m");

// Wait for completion (in coroutine)
while (rsc.loading) { yield null; }

// Access data
local data = rsc.find("040/config/title_mode_top.psb.m");
local items = data.root.items;

// Cleanup
rsc.unload();
Method / PropertyDescription
Resource() Constructor. Creates a new resource loader instance.
.load(path, ...) Begin loading one or more PSB files asynchronously. Accepts multiple path arguments.
.loading Boolean property. true while any resource is still loading.
.find(path) Retrieve loaded data by path. Returns object with .root table.
.unload() Release all loaded resources.

util_load_config(path)

High-level wrapper that loads a PSB config file synchronously (with internal caching). Returns a deep copy of the .root table — safe to modify. 

// Typical usage
local config = ::util_load_config( ::conv_path("config/title_mode_top.psb") );
local titleNum = config.titleNum;
local items = config.items;

Internally uses ResourceCache (see section 9) to avoid reloading the same file multiple times. The returned table is a deep copy via copy_PSBValue(), so modifications do not affect the cache.

util_load_psb_get_by_instance(path)

Variant that returns the raw PSB resource instance (not a copy). Used when you need to reference the same data from multiple places without copying overhead.

3. Script Loading

util_load_script(path)

Compiles and executes a Squirrel .nut script file. Functions and classes defined in the script become available in the root table. This is the only way to dynamically load code at runtime. 

// Load a mode script
::util_load_script( ::conv_path("script/mode_normal.nut") );

// Load a pack-specific script (explicit path, bypassing conv_path)
local pack_path = format("%03d/script/pack_config.nut", dev_id);
local checked = ::conv_checked_path(pack_path);
if (checked != null) {
    ::util_load_script(checked);
    // Functions defined in pack_config.nut are now callable
    local config = ::get_pack_title_mode_top();
}
Implementation note util_load_script() is a native C++ function registered into the VM, not a Squirrel-defined wrapper. It is the m2engage equivalent of Squirrel's standard dofile(), which has been removed from this VM.

4. File Existence Checks

Two native classes provide file existence checking. Both return a directory prefix string if found, or null if not.

FileUtil.getExistFileDirInMountArchive(path)

Checks if a file exists within mounted archives (e.g., alldata.bin). 

local dir = FileUtil.getExistFileDirInMountArchive("040/config/title_prof.psb.m");
// Returns: "" (empty string = found at root) or null (not found)

GameContent.getExistFileDir(path)

Checks if a file exists in extracted game content directories on the filesystem. 

local dir = GameContent.getExistFileDir("042/script/pack_config.nut");
// Returns: directory prefix string or null

conv_checked_path() calls both in sequence (archive first, then filesystem), so you rarely need to call these directly.

6. Directory Listing

host_listup_files(directory)

Lists files in a directory. Returns an array of filename strings, or null if the directory doesn't exist. This is a native C++ function — the only way to enumerate directory contents from Squirrel. 

// Only known usage in the codebase (emulator.nut:1500)
local file_lists = ::g_emu_task.host_listup_files(".");
if (null != file_lists) {
    for (local no = 0; no < file_lists.len(); no++) {
        if (file_lists[no].find(base_name) != null) {
            load_lists.append(file_lists[no]);
        }
    }
}
Practical details
  • Returns flat filenames (not full paths, not recursive)
  • Only used with "." in practice — relative to m2engage working directory
  • No wildcard/glob support — filtering must be done in Squirrel (e.g., .find())
  • No way to distinguish files from directories in the returned list
  • Available via g_emu_task.host_listup_files() (thread-safe)
Limited scope This function operates relative to the m2engage working directory. It cannot enumerate arbitrary filesystem paths outside the game content structure.

6b. Reading File Contents

No general-purpose file reading There is no function to read the contents of a text file, JSON file, or arbitrary binary file from Squirrel scripts. The complete list of host_* functions registered in the m2engage binary is: 
host_listup_files             # directory listing
host_save_statedata_image     # save emulator state (opaque binary)
host_load_statedata_image     # load emulator state (opaque binary)
host_save_statedata_rawimage  # save raw state image
host_load_statedata_rawimage  # load raw state image
host_save_sqstruct_image      # save Struct to file
host_load_sqstruct_image      # load Struct from file
host_save_sram_image          # save SRAM data

All host_load_* functions load opaque binary data into native Struct objects — not into Squirrel strings or tables. They are designed for emulator state persistence, not for reading configuration or data files.

How data gets into Squirrel

There are exactly two paths for getting file data into Squirrel scripts:

MechanismFile TypesReturns
util_load_config() / Resource() .psb.m files (encrypted PSB) Squirrel table (key-value data from PSB)
util_load_script() .nut / .nut.m files (Squirrel scripts) Executes code — functions/classes become available in root table

If you need to get custom data into the VM, you have two options:

  1. Pack it as a PSB — Convert JSON to .psb.m using mzstool.py, then load with util_load_config()
  2. Encode it in a .nut script — Define data as Squirrel table literals in a .nut file, then execute with util_load_script(). This is the approach used by dynamic pack configs (pack_config.nut).
compilestring() The string "compilestring" exists in the m2engage binary, suggesting it may be partially present. However, it is not usable from scripts in practice — standard Squirrel I/O registration is stripped, and no script in the codebase attempts to use it.

7. Binary & Struct Utilities

Struct Class (Native)

Wraps a loaded PSB resource as a typed binary structure with field access. 

// Create from loaded resource
local st = Struct(resource_data);
local root = st.getRoot();
local field = st["root"]["fieldname"];

BinaryUtil (Native)

MethodDescription
BinaryUtil.Struct2Struct(dst, src) Copy binary data between two Struct instances
BinaryUtil.StoreBitmapImage(capture, field, w, h, pitch) Store bitmap pixel data into a struct field

Table/Struct Conversion (Squirrel)

FunctionDescription
copy_PSBValue(src) Deep copy any PSB value (table, array, string, number)
copy_Struct2Table(struct) Convert a native Struct to a plain Squirrel table
setField_Table2Struct(dst, src) Write table field values into a Struct’s fields

8. Path String Parsing

fileparse(pathname)

Splits a file path string into its components. Defined in Squirrel (utils.nut), not native. 

// Signature
function fileparse(pathname)
// Returns: { path = "dir/", name = "filename", ext = ".ext" }

// Examples
fileparse("system/config/title.psb")
// → { path: "system/config/", name: "title", ext: ".psb" }

fileparse("roms/game.pce")
// → { path: "roms/", name: "game", ext: ".pce" }

9. ResourceCache Class

A Squirrel class (defined in utils.nut) that manages Resource() instances with path-based caching. Avoids reloading PSB files that are already in memory. 

class ResourceCache {
    m_rsc = null;       // Internal Resource() instance
    m_path = [];        // Currently cached path list

    function init(_path)    // Load path or array of paths (skips if unchanged)
    function get(_path)     // Get loaded resource by path (.root to access data)
}

Global instances used by the system:

InstancePurpose
s_rsc_game_content Caches game content config PSBs (title_prof, title_session, etc.)
s_rsc_title Caches title-specific resources
s_loaded_config Table-based cache for util_load_config() results (path → data)

10. Limitations & What You Cannot Do

Stripped from the VM

Standard Squirrel FeatureStatus
dofile(path) Removed. Use util_load_script() instead.
loadfile(path) Removed. No equivalent.
compilestring(code) Removed. Cannot compile code from strings at runtime.
io.open() / file() Removed. No direct file read/write.
blob() for file I/O Removed. Blobs exist in-memory only (via BinaryUtil).

Cannot Do

  • Read arbitrary files — Cannot open/read files outside the PSB/resource system
  • Write arbitrary files — Only save state functions write to disk
  • Create directories — No mkdir equivalent
  • Delete files — No remove / unlink
  • Enumerate arbitrary directories — host_listup_files() is limited to game content paths
  • Network I/O — No sockets, HTTP, or network access
  • Execute system commands — No system() or popen()
  • Dynamic code compilation — No eval or runtime code generation

Squirrel Version

m2engage embeds Squirrel 2.2.4 (not the current 3.x series). This means some newer Squirrel features are unavailable. The VM is statically linked into the m2engage binary — there is no external .so or .dll.
